# Access Request System

Система учёта заявок сотрудников на временный доступ к сайтам и интернет-сервисам
с реальной блокировкой трафика на уровне сети.

Сотрудник заполняет анкету и подаёт заявку на доступ к сервису на определённый срок,
администратор одобряет или отклоняет её, а прокси-агент на компьютере пользователя
пропускает или блокирует сайты в соответствии с решением. После окончания срока
доступ закрывается автоматически.

Проект разработан в рамках технологической практики (КТЦ Белорусской железной дороги, 2026).

## Возможности

- Регистрация, вход, роли **Сотрудник** и **Администратор** (JWT)
- Анкета сотрудника (ФИО, должность, подразделение)
- Заявки на доступ к сервису из справочника или к произвольному сайту, с периодом действия
- Жизненный цикл заявки: `Pending → Approved / Rejected → Expired`, история изменений
- Фоновая задача, автоматически переводящая истёкшие заявки в `Expired`
- Справочник сервисов (CRUD для администратора)
- Прокси-сервер с авторизацией сотрудника (логин/пароль учётной записи системы),
  проверкой каждого домена через API, кэшированием решений и журналом обращений в БД
- SSO: после входа в прокси сотрудник автоматически авторизуется в веб-интерфейсе
- Страница блокировки со ссылкой на подачу заявки
- Журнал доступа в админ-панели
- Swagger для тестирования API без UI

## Архитектура

```
┌──────────────┐  HTTP + JWT   ┌──────────────────────────────┐      ┌────────────┐
│  UI (MVC)    │ ────────────▶ │  API (ASP.NET Core Web API)  │ ───▶ │ PostgreSQL │
│  cookie-auth │               │  BLL · DAL (EF Core) · Domain │      └────────────┘
└──────────────┘               └──────────────────────────────┘
                                          ▲
                         GET /api/access/check?domain=...
                                          │
                               ┌────────────────────┐
                               │  ProxyAgent        │  ◀── браузер пользователя
                               │  Titanium.Web.Proxy│      (прокси 127.0.0.1:8000)
                               └────────────────────┘
```

| Проект | Назначение |
|---|---|
| `AccessRequestSystem.Domain` | Сущности и перечисления |
| `AccessRequestSystem.DAL` | EF Core, `AppDbContext`, конфигурации, репозитории |
| `AccessRequestSystem.BLL` | Бизнес-логика, DTO, сервисы, правила смены статусов |
| `AccessRequestSystem.API` | Контроллеры, JWT, Swagger, middleware ошибок, фоновые задачи |
| `AccessRequestSystem.UI` | ASP.NET Core MVC, Razor + Bootstrap, обращается к API по HTTP |
| `AccessRequestSystem.ProxyAgent` | Консольный HTTP(S)-прокси, пропускает/блокирует сайты по решению API |

API, UI и агент — три независимых процесса, общаются только по HTTP.

## Запуск

**Требования:** .NET 8 SDK, PostgreSQL (или Docker), `dotnet-ef`
(`dotnet tool install --global dotnet-ef`).

1. **База данных** — проще всего через Docker:
   ```bash
   docker compose up -d
   ```
   Строка подключения по умолчанию — в `src/AccessRequestSystem.API/appsettings.json`.

2. **Миграции** (один раз):
   ```bash
   dotnet ef migrations add InitialCreate -p src/AccessRequestSystem.DAL -s src/AccessRequestSystem.API
   ```
   Применять вручную не нужно — API выполняет `Database.MigrateAsync()` при старте.

3. **API** → `https://localhost:7100`, Swagger — `https://localhost:7100/swagger`
   ```bash
   dotnet run --project src/AccessRequestSystem.API
   ```
   При первом запуске создаются роли и тестовый администратор
   `admin@company.local` / `Admin123!`.

4. **UI** → `https://localhost:7050`
   ```bash
   dotnet run --project src/AccessRequestSystem.UI
   ```

5. **ProxyAgent** (по желанию) → прокси на `127.0.0.1:8000`
   ```bash
   dotnet run --project src/AccessRequestSystem.ProxyAgent
   ```

В Visual Studio можно открыть `AccessRequestSystem.sln` и включить запуск нескольких
проектов: *Свойства решения → Несколько запускаемых проектов* → API, UI, ProxyAgent.

> Перед реальным использованием замените `Jwt:Key` в `appsettings.json` на свою
> случайную строку длиной от 32 символов.

## Сценарий проверки

1. Зарегистрируйтесь в UI как сотрудник и заполните анкету.
2. Подайте заявку на доступ к сайту, укажите период.
3. Войдите как `admin@company.local` и одобрите заявку в разделе «Все заявки».
4. Запустите ProxyAgent и браузер через прокси, например
   `chrome.exe --proxy-server=127.0.0.1:8000`. Браузер запросит логин и пароль —
   введите данные сотрудника. Неодобренные сайты перенаправляются на страницу
   блокировки, одобренные открываются. Журнал обращений — в UI, раздел «Логи доступа».
5. После теста уберите прокси из настроек браузера.

### Как работает прокси

- Слушает порт `Proxy:Port` (по умолчанию 8000) на всех интерфейсах, поэтому может
  работать и локально, и как общий прокси-сервер организации.
- Каждый пользователь проходит Basic-аутентификацию прокси учётной записью системы;
  агент получает JWT в API и кэширует сессию на `Proxy:TokenCacheMinutes` минут.
- HTTPS расшифровывается, поэтому в журнал попадает полный URL. При первом запуске
  создаётся корневой сертификат и экспортируется в `proxy-root-cert.cer` рядом с
  программой — его нужно добавить в доверенные корневые центры сертификации.
- Решение «пропустить/заблокировать» кэшируется на `Proxy:CacheSeconds` секунд.

## Тестирование API без UI

```bash
curl -X POST https://localhost:7100/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@company.local","password":"Admin123!"}'
```
Полученный токен передаётся в заголовке `Authorization: Bearer <token>`.
